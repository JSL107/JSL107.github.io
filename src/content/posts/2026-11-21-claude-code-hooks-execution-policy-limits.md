코딩 에이전트에게 “작업이 끝나면 테스트까지 돌려라”라고 적어 둬도, 어느 날은 파일 몇 개만 고치고 “완료했다”고 말해요. 이 글에서는 Claude Code Hooks의 이벤트·설정·출력 계약을 바탕으로, 멀티 에이전트 백엔드 시스템의 실행 정책에 어떻게 대입할 수 있을지 살펴봐요. 실제 레포에 hook을 붙여 운영해 본 결과는 아니에요.

## 좋은 지침만으로는 실행면을 닫을 수 없다

LLM 에이전트 시스템을 운영하다 보면 같은 규칙을 여러 번 쓰게 돼요. 비밀 파일은 건드리지 말 것. CLI를 실행할 때는 격리된 환경을 쓸 것. 작업이 끝났다고 말하기 전에 lint, test, build를 통과시킬 것. 문서에 적기는 쉽지만 문서만 마지막 방어선으로 삼을 수는 없어요.

모델은 매 순간 지침 파일과 대화 내용, 현재 파일, 이전 실패 로그를 보고 다음 행동을 추론해요. 하지만 실제 명령을 실행할 때는 별도의 결정론적 검사 없이 넘어갈 수 있어요. “테스트를 꼭 실행하라”는 모델이 판단할 때 참고하는 힌트이고 “테스트가 실패하면 종료하지 못한다”는 실행면에 걸린 제약이에요.

Claude Code Hooks는 바로 이 지점을 겨냥해요. Hook은 세션 시작, 사용자 프롬프트 제출, 툴 실행 전후, 종료 시점처럼 Claude Code의 정해진 lifecycle event마다 사용자 정의 로직을 실행해요. 모델에게 더 자세히 설명하는 대신 특정 순간에 검사를 거는 방식이에요.

## Hook은 에이전트 실행 루프 앞뒤에서 움직인다

백엔드 개발자의 언어로 바꾸면 hook은 에이전트 실행 루프 앞뒤에 붙는 작은 미들웨어예요. 대표적인 이벤트가 `PreToolUse`와 `PostToolUse`예요. `PreToolUse`는 `Bash`, `Edit`, `Write` 같은 툴을 실행하기 전에 호출돼요. 명령 문자열이나 파일 경로를 살펴보고 위험하면 차단할 수 있어요. `PostToolUse`는 툴이 성공한 뒤 호출되며 포맷터를 실행하거나 감사 로그를 남기고 수정된 파일을 추가로 검사할 때 쓸 수 있어요.

공식 가이드의 자동 포맷 예시를 보면 이 구조가 드러나요.

```json
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write"
          }
        ]
      }
    ]
  }
}
```

`Edit` 또는 `Write`가 성공하면 hook 입력 JSON에서 `tool_input.file_path`를 꺼내 `prettier`를 실행해요. 작업 결과를 저장한 뒤 후처리 파이프라인을 태우는 구조예요. PR 리뷰 초안이나 업무 로그를 만드는 모델 출력 자체를 바꾸지는 않지만 파일을 바꾼 뒤 형식을 검사하는 일은 모델의 성실성에 맡기지 않아도 돼요.

## 권한 설정과 hook은 서로 다른 기준으로 검사한다

Claude Code에는 permission allow/deny도 있어요. 권한 설정은 주로 어떤 툴이나 명령 패턴을 허용할지 선언해요. Hook은 JSON 입력을 받아 구체적인 맥락까지 살필 수 있어요. 같은 `Bash`라도 명령 문자열에 따라, 같은 `Write`라도 파일 경로에 따라 다른 결정을 내릴 수 있어요.

공식 reference의 `PreToolUse` 예시에서는 `rm -rf`를 차단해요.

```bash
#!/bin/bash
# .claude/hooks/block-rm.sh
COMMAND=$(jq -r '.tool_input.command')

if echo "$COMMAND" | grep -q 'rm -rf'; then
  jq -n '{
    hookSpecificOutput: {
      hookEventName: "PreToolUse",
      permissionDecision: "deny",
      permissionDecisionReason: "Destructive command blocked by hook"
    }
  }'
else
  exit 0 # no decision; normal permission flow applies
fi
```

핵심은 `permissionDecision: "deny"`예요. Hook은 stderr에 경고만 남기는 게 아니라 Claude Code가 이해하는 출력 계약을 통해 툴 호출을 막아요. 내 시스템이라면 CLI 호출 앞에서 “특정 환경 변수를 넘기지 말라”, “프롬프트를 argv에 싣지 말라” 같은 검사를 거는 것과 비슷해요. 다만 Claude Code Hook은 Claude Code 내부 툴 실행에 붙으므로 서버 애플리케이션의 자체 실행 계층까지 자동으로 보호하지는 않아요.

## 배포 위치는 정책의 소유자를 정한다

Claude Code 설정은 사용자 전체 설정, 공유 프로젝트 설정, 프로젝트 로컬 설정으로 나뉘어요. `~/.claude/settings.json`은 한 개발자의 모든 프로젝트에 적용돼요. `.claude/settings.json`은 프로젝트에서 버전 관리할 수 있어요. `.claude/settings.local.json`은 특정 프로젝트에서 개인에게만 적용되는 예외나 승인 기록에 가까워요.

이 구분은 누가 정책을 관리하느냐와 이어져요. 개인이 선호하는 알림 방식은 사용자 설정에 둬도 돼요. 팀이 함께 지켜야 하는 파일 보호 규칙과 공통 포맷 후처리, 종료 전 검증은 공유 프로젝트 설정에 둬야 리뷰와 변경 이력이 남아요. 개인의 일시적인 승인 기록을 공유 설정에 넣으면 팀 전체의 실행 정책이 의도치 않게 느슨해져요.

공식 가이드의 보호 파일 예시는 `.env`, lockfile, `.git/` 같은 경로를 `PreToolUse`에서 막고 그 hook을 프로젝트 설정에 등록해요.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/protect-files.sh"
          }
        ]
      }
    ]
  }
}
```

이 예시는 “비밀 파일을 읽지 말아야 한다”는 일반 지침이 아니에요. `Edit` 또는 `Write`가 그 경로를 대상으로 할 때 실행 전에 막는 정책이에요. Slack 기반 멀티 에이전트 시스템에 대입하면 토큰과 환경변수 파일을 코드 리뷰 규칙으로만 지키는 데 그치지 않고 실제 편집 경로에서도 한 번 더 검사하는 셈이에요.

## 내 시스템에 바로 닿는 곳과 닿지 않는 곳

내가 운영하는 Slack 기반 멀티 에이전트 시스템에는 에이전트 실행을 시작하고 모델 호출을 태운 뒤 성공·실패와 근거를 남기는 생명주기가 있어요. Claude Code Hooks가 그 내부 구현을 대체하지는 않아요. 대신 로컬 코딩 에이전트가 파일과 명령을 다루는 루프에서 비슷한 역할을 해요.

CLI provider 격리에도 적용해 볼 수 있어요. 이 시스템은 모델 CLI를 실행할 때 작업 디렉터리, `HOME`, 인증 디렉터리, 환경변수 전달 범위를 제한해요. Hook으로 Claude Code가 `Bash`에서 특정 CLI를 호출하는 순간을 검사할 수 있어요. 프롬프트를 argv로 넘기는 명령 패턴을 막거나 알려진 문제가 있는 경로에서의 실행을 차단하는 식이에요. 다만 실제 hook 입력에 현재 디렉터리와 명령이 어떤 형태로 들어오는지 확인해야 정책을 정확히 만들 수 있어요.

코드를 바꾼 뒤 lint, test, build를 통과해야 한다는 개발 규칙에도 적용할 수 있어요. 종료 시점에 검증을 걸면 PR 리뷰, 작업 로그, 배포 전 미리보기처럼 결과의 신뢰도가 중요한 자동화에서 에이전트가 검증을 기억했는지에 덜 의존하게 돼요.

자연어 날짜를 해석해 일정을 등록하는 기능처럼 LLM을 쓰지 않거나 서버 내부에서 이미 결정론적으로 계산하는 작업은 Claude Code Hook의 대상이 아니에요. Hook이 제어하는 범위는 Claude Code 세션의 툴 실행이에요. 운영 서버의 실행 생명주기와 권한은 애플리케이션 내부에서 설계해야 해요.

## 종료 전 검증은 조건을 좁혀야 한다

`Stop`은 에이전트가 응답을 마치려는 시점에 검사를 걸 수 있어서 “수정은 했지만 테스트는 안 돌렸다”는 문제와 직접 맞닿아요. 하지만 종료할 때마다 `pnpm lint:check && pnpm test && pnpm build`를 실행하면 작은 문서 수정에도 긴 검증이 붙어요. 검증에 실패했을 때 어떻게 재시도할지, 명령 자체가 불안정하거나 오래 걸릴 때는 어떻게 처리할지도 정해야 해요.

모든 응답이 끝나기 전에 전체 검증을 돌리기보다는 코드 파일이 바뀐 세션에서만 검증하는 편이 더 현실적이에요. `package.json`이나 스키마가 바뀌었을 때 문서 동기화 검사까지 추가하는 식으로 조건을 좁힐 수도 있어요. Hook은 정해진 대로 실행되지만 어떤 조건에서 실행할지는 설계해야 해요.

| 정책 | hook으로 적합한가 | 이유 |
| --- | --- | --- |
| `.env` 편집 금지 | 적합 | `Edit`·`Write` 직전 파일 경로를 검사해 차단할 수 있다 |
| 위험한 쉘 명령 차단 | 적합 | `Bash` 직전 명령 문자열을 검사할 수 있다 |
| non-ASCII 경로에서 특정 CLI 실행 금지 | 부분적으로 적합 | `Bash` 명령은 검사할 수 있지만 실제 작업 디렉터리와 경로 정보가 hook 입력에 어떻게 들어오는지는 적용 전 확인이 필요하다 |
| 모든 종료 전 전체 테스트 강제 | 가능하지만 신중 | `Stop` 계열 게이트로 설계할 수 있으나 비용·실패 처리·문서 작업 예외를 정해야 한다 |

## 공유 hook은 실행 코드로 리뷰해야 한다

Hook은 안전장치이면서 실행 가능한 코드예요. command hook은 사용자의 권한으로 로컬 명령을 실행해요. 공유 프로젝트 설정에 들어간 hook은 팀원이 저장소를 신뢰하고 실행하면 각자의 머신에서 돌 수 있어요. 그래서 `.claude/settings.json`도 정책 코드처럼 리뷰해야 해요.

`curl | bash` 형태의 hook, 원격 스크립트를 내려받아 실행하는 hook, 변경된 파일 경로를 따옴표 없이 쉘에 넘기는 hook은 새로운 공격면이 돼요. 공식 가이드의 예시도 `jq` 같은 로컬 도구를 전제로 해요. 필요한 도구가 없으면 hook이 실패할 수 있고 실패 코드가 항상 차단을 뜻하지도 않아요. Blake Crosley의 글이 지적하듯 exit code의 의미를 잘못 이해하면 “실패했으니 막혔겠지”라고 착각할 수 있어요.

처음에는 관찰용 hook으로 입력 JSON과 이벤트 발생 시점을 확인할 수 있어요. 그다음 `.env` 편집 금지처럼 오탐 비용이 낮고 효과가 큰 정책을 차단 모드로 바꾸고, 종료 전 검증처럼 비용이 큰 정책은 조건부로 붙여요.

## 다음에 확인할 것

먼저 공식 보호 파일 예시를 따라 `.env` 편집 차단 hook을 만들어요. 이어서 `Bash`용 관찰 hook으로 특정 CLI를 실행할 때 입력 JSON에 어떤 필드가 들어오는지 기록해요. 이를 확인해야 non-ASCII 경로에서의 실행을 hook으로 정확히 금지할 수 있는지 판단할 수 있어요.

마지막으로 코드 파일이 바뀐 경우에만 종료 전 검증을 거는 실험을 해요. 전체 테스트를 매번 돌릴지, 빠른 lint부터 돌릴지 판단할 수 있도록 검증 비용도 함께 재요.
