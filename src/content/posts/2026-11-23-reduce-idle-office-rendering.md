맥 콘솔에 3D 오피스를 추가하자 사용자가 아무것도 하지 않을 때도 합계 CPU 사용량이 151.8%까지 올랐어요. 대부분의 직원은 앉아 있고 벽과 가구도 움직이지 않는데 렌더러는 매 프레임 장면 전체를 다시 그리고 있었죠.

장면이 바뀔 때만 렌더링하고 정적 객체를 묶었어요. 탭을 전환해도 웹뷰가 유지되도록 수명도 조정했어요. 기록상 같은 조건에서 측정한 합계 CPU 사용량은 30.1%로 내려갔어요.

### CPU를 프로세스별로 다시 세다

초기 기록에는 CPU 사용량이 “약 72%”라고 적혀 있었어요. 전체 비용이 아니라 WebContent 프로세스만 측정한 값이었죠. GPU 프로세스와 앱 프로세스까지 포함해 다시 측정한 결과는 다음과 같아요.

| 측정 대상 | CPU 사용량 |
|---|---:|
| WebContent | 74.9% |
| GPU | 74.0% |
| 앱 | 2.8% |
| 합계 | 151.8% |
| 비교 대상인 2D 화면 | 20.5% |

960×1050 크기의 창에서 1초 간격으로 표본 60개를 모았어요. 측정 시간은 60초예요. 합계는 WebContent·GPU·앱 프로세스의 사용량을 모두 더한 값이라 100%를 넘을 수 있어요. 이번에는 GPU 프로세스도 WebContent와 거의 같은 수준으로 CPU를 쓰고 있었어요. WebContent만 보면 렌더링 비용의 절반가량을 놓치는 셈이죠.

이 수치는 제공된 PR 기록의 1차 측정 결과예요. 기록에는 하드웨어 모델, macOS 버전, 전원 설정, 화면 배율이 없어 151.8%라는 절댓값이 다른 환경에서도 재현된다고 단정할 수는 없어요. 여기서는 기록상 “같은 조건”에서 측정한 변경 전후 값을 비교해요.

### 병목은 장면의 복잡도보다 렌더링 시점에 있었다

`renderer3d.js`에서 `draw`는 매 프레임 `webgl.render`를 호출했어요. 한 번 렌더링할 때 그림자 지도를 포함해 9,894번의 그리기 호출이 발생했죠. 복잡한 장면을 한 번 그리는 데도 비용이 들지만 장면이 그대로인데도 그 비용을 계속 치르는 게 더 큰 문제였어요.

직원이 앉아 있고 입력도 없고 카메라도 움직이지 않는다면 연속된 프레임의 결과는 대부분 같아요. 그런데 기존 구조에는 다음 프레임이 필요한지 판단하는 조건이 없었어요. 객체 수를 줄이거나 품질을 낮출 수도 있지만 정지 시간이 긴 오피스 화면에서는 렌더링 빈도를 줄이는 편이 더 직접적이었죠. 사용자 입력이나 상태 변화가 생길 때만 새 프레임을 만들면 반복 비용을 없앨 수 있으니까요.

### 변화가 있을 때만 렌더링하다

이전에는 프레임 루프가 돌 때마다 장면 전체를 그렸어요. 바꾼 뒤에는 화면에 실제 변화가 있을 때만 렌더링해요. 아래 코드는 PR의 실제 구현을 그대로 옮긴 게 아니라 변경 전략을 설명하려고 축약한 예시예요.

```javascript
let renderRequired = true;
function invalidateScene() {
renderRequired = true;
}
function frame() {
if (renderRequired) {
webgl.render(scene, camera);
renderRequired = false;
}
requestAnimationFrame(frame);
}
```

중요한 건 `requestAnimationFrame`을 쓰느냐보다 어떤 조건에서 `webgl.render`를 호출하느냐예요. 직원 상태가 바뀌거나 사용자가 방을 확대하고 카메라를 움직이는 등 출력이 달라지면 `renderRequired`를 다시 켜요. 아무 변화가 없다면 다음 프레임 콜백이 와도 9,894개의 그리기 호출을 다시 만들 필요가 없어요.

이 전략은 정지해 있는 시간이 긴 화면에 잘 맞아요. 카메라가 계속 움직이거나 모든 객체에 애니메이션이 늘 재생되는 장면은 거의 매 프레임 바뀌니 이점이 줄어들어요.

### 벽과 가구를 묶어 그리다

움직이지 않는 객체도 묶었어요. 오피스의 벽과 가구는 직원 상태가 달라져도 위치와 형태가 그대로예요. 이런 객체를 각각 그리면 렌더링할 때마다 호출 비용이 쌓여서 고정된 물체를 한 덩어리로 묶어 그리도록 바꿨어요.

정적 객체를 묶는 데도 대가는 있어요. 일부 가구만 자주 바꾸거나 객체별로 선택·가시성을 제어해야 한다면 큰 묶음을 다시 만들거나 따로 관리해야 해요. 이번에는 벽과 가구가 움직이지 않는 오피스였으니 그 대가보다 렌더링 호출을 줄이는 일이 더 중요했어요.

### 탭을 바꿔도 웹뷰를 유지하다

성능 문제와 함께, 탭을 전환하면 직원 위치가 초기화되는 문제도 있었어요. 원인은 상태 직렬화보다 뷰의 소유권 구조에 가까웠어요.

기존에는 `OfficeView`가 `@StateObject`로 `Office3DController`와 웹뷰를 소유했어요. 상위의 `AppRootView`는 현재 탭에 따라 `switch`로 화면을 교체했고요. 사용자가 오피스 탭을 떠나면 `OfficeView`가 화면 계층에서 사라지면서 그 뷰가 소유한 웹뷰도 폐기됐어요. 다시 돌아왔을 때 문서를 새로 불러오니 걷던 직원도 초기 위치로 돌아간 거죠.

3D 화면을 담은 웹뷰는 탭보다 오래 유지되는 상위 뷰가 소유하도록 옮겼어요. 이제 탭을 전환할 때 같은 웹뷰를 보이거나 숨겨요. 3D 문서와 그 안의 직원 위치도 그대로 유지돼요. 구조를 단순화하면 아래와 같아요.

```text
변경 전
AppRootView
└─ switch로 OfficeView 생성·제거
└─ Office3DController + WebView 소유
변경 후
AppRootView 또는 더 오래 사는 상위 뷰
├─ Office3DController + WebView 소유
└─ 탭은 기존 인스턴스의 표시 여부만 전환
```

이 방식은 재생성 비용과 상태 유실을 줄여 주지만 다른 탭을 보는 동안에도 웹뷰 인스턴스가 메모리에 남아요. 메모리보다 복귀 속도와 상태 보존이 중요한 화면에는 맞지만 자주 쓰지 않는 무거운 화면이 여럿이라면 부담이 될 수 있어요. 그럴 때는 상태를 명시적으로 저장하고 필요할 때 웹뷰를 복원하는 방법도 검토해야 해요.

### 2D 연출을 사건 기반으로 옮기다

CPU 사용량을 낮춘 뒤에는 2D 오피스에만 있던 연출을 3D로 옮겼어요. 2D에 있던 후보 18가지 가운데 일곱 가지를 골랐어요.

| 연출 | 3D에서 표현한 동작 |
|---|---|
| 인계 | 받는 사람의 책상까지 걸어갔다가 복귀 |
| 거절 | 좌우 흔들림과 `!` 표시 |
| 접수 대기 | 대기 상태를 나타내는 점 |
| 완료 | 직원이 튀어오르는 동작 |
| 실패 | 고개를 떨구는 자세 |
| 저녁·밤 | 책상 스탠드 점등 |
| 주간 기억 청소 | 청소 로봇과 먼지 표현 |

모델에 애니메이션을 추가하는 것만으로는 이 기능들을 옮길 수 없었어요. 기존 3D 경로는 `OfficeHosting.swift`의 `officeHostedEventMessage`를 거쳐 `stateChanged`만 전달했어요. 인계와 거절 같은 연출은 앱이 `visualIntents`로 계산한 뒤 2D 씬의 `scene.perform`에만 넘기고 있었죠.

접수 대기와 완료 상태를 판단하는 `ConsoleStore.pendingCommands`도 3D로 전달하지 않았어요. 스냅샷의 `housekeeping` 값은 3D까지 도착했지만 `live.js`가 읽지 않았고요. 실패 상태와 시간대는 이미 전달하고 있었으나 자세와 책상 조명으로 표현하지 않았어요.

3D에서 같은 의미를 표현하려면 직원의 단순 상태뿐 아니라 시각적 의도, 명령 진행 단계, 청소 상태도 전달해야 했어요. 이미 들어오는 실패와 시간대 정보도 렌더링에 반영해야 했고요.

18가지를 모두 옮기지 않은 이유는 실행 빈도예요. 인계, 거절, 완료 같은 동작은 특정 사건이 생겼을 때만 잠시 실행돼요. 반면 앉아 있는 직원의 숨쉬기와 타이핑을 계속 재생하면 장면이 매 프레임 달라져 변경 기반 렌더링의 이점이 줄어들 수 있어요. CPU를 30.1%까지 낮춘 성능 경계를 지키려고 숨쉬기와 타이핑은 3D로 옮기지 않았어요.

상시 애니메이션이 꼭 필요하다면 프레임 속도를 낮추거나 화면에 보이는 직원만 움직이고 일부 애니메이션을 셰이더에서 처리하는 방법도 실험할 수 있어요. 다만 이번 PR에는 이런 대안을 구현하거나 측정한 결과가 없어요.

### 결과와 남은 확인 작업

최종 측정에서 3D 오피스의 합계 CPU 사용량은 같은 조건을 기준으로 151.8%에서 30.1%로 낮아졌어요. 입력된 측정값으로 계산하면 121.7%포인트, 기존보다 약 80.2% 줄어든 거예요. 2D 화면의 20.5%보다는 여전히 9.6%포인트 높아요. 탭을 전환한 뒤에도 직원 위치가 유지되는 것도 확인했어요.

30.1%를 변경 기반 렌더링 하나만의 효과로 해석할 수는 없어요. 렌더링 시점 제한과 정적 객체 묶음을 함께 적용했고 후속 연출에서는 상시 애니메이션을 제외했으니까요. 변경 전에는 한 번 렌더링할 때 그리기 호출이 9,894회였지만 변경 후 호출 횟수와 각 개선의 기여도는 기록돼 있지 않아요.

반복 탭 전환, 이벤트 중복 수신, 웹뷰 재시작, 앱 재실행까지 포함한 상태 보존 결과도 기록돼 있지 않아요. 일곱 가지 연출을 동시에 또는 연속으로 실행했을 때의 CPU 값과 상시 애니메이션을 포함했을 때의 성능 변화도 측정하지 않았어요.

후속 실험에서는 렌더링 시점 변경과 정적 객체 묶음을 하나씩 켜고 끄면서 CPU와 그리기 호출 수를 다시 측정해야 해요. 연출 실행과 웹뷰 재시작 조건도 따로 검증해야 해요.
