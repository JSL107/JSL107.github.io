GitHub나 Notion의 상태 변화를 감지해 사용자에게 제안 카드를 보여 주는 시스템에서, 기존 LLM의 판정을 더 가벼운 로컬 결정 모델인 Kev로 바꾸려 했어요. 이번 변경은 운영 판정을 LLM에 맡겨 둔 채, 두 모델을 비교하고 문턱값을 보정할 데이터를 모으는 데 범위를 뒀어요.

## 판정 결과만으로는 모델을 교체할 수 없다

기존에는 LLM이 변경 사항을 하나씩 검토해 카드를 올릴지 버릴지 결정했어요. 비용을 줄이고 응답 속도를 높이려고 Kev로 대체하려면, 같은 입력에 두 모델이 각각 어떤 결정을 내렸는지 알아야 해요. 판단이 엇갈렸다면 어느 쪽이 사람의 판단에 더 가까웠는지도 설명할 수 있어야 하고요.

이전의 shadow mode는 두 모델의 판단이 몇 건 달랐는지만 로그 한 줄로 남겼어요. “오늘 12건이 달랐다”는 기록으로는 어떤 입력에서 판단이 엇갈렸는지, Kev의 점수가 문턱 근처였는지, 같은 PR의 여러 변경을 중복으로 집계했는지 되짚을 수 없어요. 건별 점수와 판정이 없으니 나중에 판별력을 계산할 수도 없었어요.

더 큰 문제는 관측 편향이었어요. 사람의 피드백인 `✅ 실행`과 `❌ 무시`는 LLM이 올린 카드에만 달렸어요. 엔진이 `promote=false`인 변경은 기록하지 않고 버렸기 때문에 LLM이 통과시킨 영역에는 사람의 판정이 쌓였지만 버린 영역에는 정답이 남지 않았어요. LLM이 고른 사례만 평가해서는 버린 사례에서 오판했을 가능성을 살펴볼 수 없어요. 모델을 교체하기 전에 풀어야 할 문제는 알고리즘 자체보다 측정 구조였어요.

## 변경 단위의 shadow 원장을 만들다

이번에는 shadow mode를 바꿔 각 변경의 Kev 점수와 LLM 판정을 한 행씩 저장하도록 했어요. 이전에는 집계 로그가 실행과 함께 사라졌지만 이제는 어떤 변경에 어떤 점수와 판정이 붙었는지 다시 분석할 수 있는 원장이 생겼어요.

Kev는 여기서 아직 운영 결정을 내리지 않아요. 흐름을 간단히 나타내면 다음과 같아요.

```text
상태 변경 감지
├─ 기존 LLM 판정 ──> 실제 카드 발송 여부 결정
└─ Kev 점수 계산 ──> shadow 원장에 비교 데이터 기록
```

이 구조에서는 Kev가 잘못 판단해도 실제 발송 결과가 달라지지 않아요. 인증이나 발송처럼 사용자에게 영향을 미치는 경계는 기존 흐름에 두고, 그 옆에 관측 장치를 붙였어요. 로컬 Kev 서버는 `pnpm kev:start`로 실행하지만 서버를 켠다고 운영 판정 권한까지 넘기는 건 아니에요. 운영 판정자는 여전히 LLM이에요.

원장에 저장된 행은 모델의 출력일 뿐, 정답은 아니에요. 사람의 판정과 연결해야 평가 자료가 돼요. 특히 기존 흐름에서 사라졌던 `promote=false` 영역의 정답을 모을 방법이 필요했어요.

## 버린 영역에서도 정답을 모으되 사용자 부담은 제한하다

LLM이 버린 변경을 모두 다시 카드로 올리면 더 완전한 비교 자료를 얻을 수 있어요. 다만 평소에는 보이지 않던 저가치 변경이 대량으로 노출될 수 있고 사용자가 카드마다 피드백해야 하는 부담도 커져요.

이번에는 전부 수집하는 대신 표본을 뽑기로 했어요. LLM이 버린 변경 중 10%를 추출하되 하루 최대 3건까지만 표본 카드로 수집해요. 표본 카드는 평소 제안 카드와 같은 형태로 보여 주므로 사용자는 기존처럼 실행할지 무시할지 판단을 남길 수 있어요.

```text
LLM이 버린 변경
└─ 10% 표본 추출
└─ 하루 최대 3건
└─ 기존 카드와 같은 형태로 피드백 수집
```

10%와 하루 3건이 이미 품질을 입증한 최적값은 아니에요. 근거 PR에서는 운영 부담을 통제하면서 버린 영역의 정답을 모으기 위한 수집 정책으로 이 제한을 제시해요. 표본량이 충분한지, 특정 시간대나 저장소에 치우치는지, 오래 유지했을 때 필요한 만큼 피드백을 확보할 수 있는지는 아직 확인되지 않았어요.

그래도 이전에는 정답을 얻을 수 없던 사례 중 일부에 대해, 실제로 버릴 만했는지 사람의 판단을 받을 수 있어요. LLM이 통과시킨 영역뿐 아니라 버린 영역에서도 제한적으로 오류를 관찰할 수 있게 된 거예요.

## 행 단위 기록을 PR 단위 보정 자료로 바꾸다

상태 변경은 행 단위로 일어나지만 사용자는 작업을 PR 단위로 인식할 수 있어요. 같은 PR에서 감지한 여러 변경을 모두 독립된 사례로 계산하면 특정 PR이 분석 결과에 지나치게 큰 영향을 줄 수 있어요.

보정 스크립트는 같은 PR에서 나온 데이터를 하나로 묶어 분석하고 그 결과를 바탕으로 Kev의 문턱값을 추천해요. 개별 점수는 분석을 재현할 수 있도록 원장에 남겨 두되, 보정할 때는 실제 작업 단위에 맞춰 판단하는 거예요.

여기서도 “추천”과 “적용”은 구분해야 해요. 스크립트가 문턱을 추천할 기반은 마련됐지만 추천값을 운영에 자동으로 반영한다는 근거는 없어요. 실제 수집 건수와 추천 문턱의 값, 기존 LLM과 비교한 정확도나 비용 절감 폭도 입력 자료에는 나오지 않아요. 이번 변경으로 “Kev의 우수성을 입증했다”거나 “운영 비용을 줄였다”고 해석해서는 안 돼요.

## 운영 전환 전에 남은 한계

행 단위 원장이 생기면서 저장하고 관리할 대상이 늘었고 표본 카드는 사용자에게 추가 판단을 요구해요. PR 단위 집계도 같은 PR을 어떻게 식별하고 묶느냐에 따라 결과가 달라질 수 있어요.

제공된 PR 설명에는 표본을 추출할 때 중복을 막는 방식, 날짜 경계에 적용하는 시간대, 프로세스를 재시작한 뒤에도 일일 한도를 유지하는지, Kev 서버에 장애가 났을 때 어떻게 처리하는지가 명시돼 있지 않아요. 이런 항목은 따로 검증해야 해요.

다음과 같은 조건에서는 이번 방식을 그대로 적용하기 어려워요.

- 버린 사례를 사용자에게 다시 노출하는 것 자체가 보안이나 개인정보 경계를 넘는 경우
- 하루 3건의 추가 카드도 사용자 경험에 큰 부담을 주는 경우
- PR처럼 여러 변경을 묶을 안정적인 식별자가 없는 경우
- 판정 기준이 불명확해 사람의 피드백을 정답으로 보기 어려운 경우
- 기존 판정 경로와 shadow 경로를 함께 실행하는 비용이 허용 범위를 넘는 경우

이런 경우에는 오프라인 라벨링이나 별도의 검수자 큐, 과거 데이터 재생 같은 대안을 검토해야 해요.

## 관측 장치 다음에는 승인 조건이 필요하다

이번 변경은 “무엇을 측정할 것인가”에는 답했지만 “어떤 결과가 나오면 Kev로 전환할 것인가”까지 정하지는 않았어요. 회고에서도 정체된 과제의 승인 조건과 조사가 끝났다고 판단할 근거를 미리 문서화하지 못한 점이 문제로 남았어요. 관측 데이터가 쌓여도 전환 기준이 없다면 shadow mode는 장기간 이어지는 실험에 머물 수 있어요.

다음 단계에서는 적어도 아래 항목부터 정해야 해요.

- 비교 기간과 필요한 최소 표본 수
- PR 단위 정답을 결정하는 규칙
- 허용할 오탐과 미탐의 기준
- 추천 문턱을 채택하거나 기각할 승인 조건
- Kev 장애 시 기존 LLM으로만 동작하는 실패 경계
- 중복 이벤트와 재시작 상황에서도 원장과 일일 표본 한도가 유지되는지 확인할 범위

특히 실패, 중복, 재시작 검증이 끝났다고 볼 근거는 아직 없어요. 별도 PR의 조건 확정과 다른 PR·이슈에 대한 조사도 회고에서 미완으로 남았으므로 관련 결론을 이번 변경의 성과에 포함해서는 안 돼요.
