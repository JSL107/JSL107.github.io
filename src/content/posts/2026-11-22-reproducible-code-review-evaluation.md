코드 리뷰 프롬프트를 고친 뒤 점수가 올랐다고 해서 리뷰 성능도 실제로 좋아졌다고 말할 수 있을까요? 모델은 실행할 때마다 다른 답을 내고, 입력 diff가 중간에서 잘렸다면 결함을 놓친 책임을 모델에만 돌리기도 어려워요. 이전 결과와 비교할 기준선조차 없다면 점수 변화가 개선인지 우연인지 판단하기 힘들어요.

이 글에서는 `review-replay`에 반복 측정, 기준선 비교, hold-out, 미탐 목록 재생, diff 잘림 분리 집계, UTF-8 바이트 단위 절단, 판정 방향 표시를 추가한 과정을 다뤄요. 근거로 삼은 것은 `personal_agents` 저장소의 PR 설명과 거기에 기록된 실측값이에요. 코드와 전체 테스트 결과는 따로 재검증하지 못했어요.

### 한 번의 점수로는 개선과 변동을 구분할 수 없었다

`pnpm review:replay`는 사람이 이미 판정한 리뷰 지적을 당시 코드에 다시 적용하는 도구예요. 오탐이라 기각한 `REJECTED` 지적이 다시 나오는지, 정탐으로 확인하고 수정한 `FIXED` 지적을 다시 찾아내는지 측정해요. 같은 표본으로 프롬프트 변경 전후를 비교할 수 있지만 처음에는 표본마다 한 번씩만 실행했어요.

문제는 리뷰 모델이 실행할 때마다 같은 결과를 내지 않는다는 점이었어요. [PR #668](https://github.com/JSL107/personal_agents/pull/668)에 기록된 실측에서는 같은 프롬프트와 코드를 세 번 실행했는데도 정탐 유지율이 60%, 80%, 60%로 달랐어요. 측정 단위는 실행 회차였고 세 회차 사이의 최대 차이는 20%p였어요. 변경 전 60%, 변경 후 80%라는 결과만 골라 보면 프롬프트가 개선됐다고 결론 내릴 수 있지만 세 번의 결과를 함께 보면 80%가 평소 실행 변동 범위 안에 있을 가능성을 배제할 수 없어요.

그래서 `--trials`를 추가했어요. 같은 표본을 N회 재생하고 회차별 재현율과 변동 범위를 보고서에 남겨요. 반복 측정으로 확률적 출력이 사라지는 건 아니지만 한 번 나온 값을 고정된 성능처럼 받아들이지 않고 관찰한 변화가 평소 변동 범위 안에 있는지 먼저 확인할 수 있어요.

`--baseline`을 지정하면 이전 JSON 보고서와 현재 결과를 직접 비교해요. 예전에도 보고서는 남겼지만 두 파일을 나란히 놓고 해석하는 일은 사람이 해야 했어요. 이제는 수치가 달라졌는지에 더해 그 변화가 기준선의 변동 범위 안인지 밖인지도 도구가 판정해요.

옵션을 지정하지 않으면 예전처럼 한 번만 실행하고 쿼터 소비도 달라지지 않아요. 반복 측정은 판단 근거를 늘리는 만큼 모델 호출 비용이 N배 가까이 들 수 있어서 프롬프트 변경을 검증하거나 기준선을 갱신하는 등 비교가 필요할 때 선택해서 쓰는 편이 맞아요.

### 정답이 프롬프트에 들어가면 회귀 테스트가 아니다

반복 횟수를 늘려도 표본 자체가 오염됐다면 결과를 믿기 어려워요. 기존 재생 구조에서는 대상 카드의 기각 사유가 학습 규약을 거쳐 프롬프트에 들어갈 수 있었어요. 과거에 “이 패턴은 오탐”이라고 판정한 이유가 재생 프롬프트에 담기면, 모델이 코드를 검토해 오탐을 피한 건지 정답에 가까운 정보를 미리 보고 답한 건지 구별하기 어려워요.

[PR #668](https://github.com/JSL107/personal_agents/pull/668)은 이를 제어하려고 `--holdout`을 추가했어요. 재생 대상 카드를 학습 규약에서 빼고 실행해 평가할 답이 입력에 섞이지 않게 했어요.

hold-out이 필요한 이유는 모델 평가에서 흔히 말하는 데이터 누수와 같아요. 반복 실행은 출력의 분산을 살피고, hold-out은 입력과 정답 사이의 부당한 연결을 끊어요. 둘은 서로 대신할 수 없어요. 오염된 표본을 여러 번 실행하면 오염된 결과만 더 정밀하게 측정하고 깨끗한 표본이라도 한 번만 실행하면 회차에 따른 변동을 알 수 없거든요.

### 이미 냈던 지적만 재생해서는 미탐을 측정할 수 없었다

기존 `review-replay`는 원장에 `pr_review_finding` 카드가 남은 `REJECTED`와 `FIXED` 지적만 재생할 수 있었어요. 모델이 한 번이라도 제기한 문제에만 카드가 생기므로 아예 발견하지 못한 결함은 재생 대상에 들어오지 않아요. 기존에 찾던 결함을 계속 찾아내는지는 확인할 수 있지만 과거에 놓친 결함을 새 프롬프트가 발견하는지는 별도 표본이 없으면 알 수 없어요.

[PR #671](https://github.com/JSL107/personal_agents/pull/671)은 외부에서 정리한 미탐 목록을 받도록 `--misses`를 추가했어요. 미탐 한 건에는 다음 필드가 들어가요.

- `repo`
- `pullNumber`
- `filePath`
- `line`
- `body`
- 선택 항목인 `headSha`

새로 추가한 순수 함수 `parseMissedFindings`는 이 구조를 검사하고 형식이 잘못된 목록은 모델 쿼터를 쓰기 전에 거부해요. 필수 필드가 빠졌거나 줄 번호를 해석할 수 없는 표본에 비용을 쓴 뒤 결과를 폐기하지 않도록 하는 평가 경계예요.

미탐 목록도 기존 카드와 같은 흐름으로 재생하고 보고서에는 오탐 재발률과 정탐 유지율에 더해 미탐 재현율을 표시해요. 기준선 비교와 반복 측정도 똑같이 적용해요. 이제 “전에 냈던 지적을 다시 내는가”뿐 아니라 “전에 놓친 결함을 이제는 찾는가”까지 평가할 수 있어요.

다만 PR 설명에 따르면 미탐 조사 자료에는 파일 이름과 줄만 적혀 있었고 기존 매칭에는 전체 경로가 일치해야 했어요. 이 차이를 어떤 경로 해석 규칙으로 해결했는지는 제공된 근거만으로 완전히 확인할 수 없어요.

### 모델이 놓친 것과 모델에게 보여 주지 않은 것을 분리했다

미탐 재현율을 계산하면서 또 다른 왜곡이 드러났어요. 과거 PR의 diff가 50,000바이트를 넘으면 모델에는 일부만 전달되는데 잘린 지점 뒤에 있는 결함까지 일반 미탐과 같은 분모에 넣고 있었어요.

[PR #679](https://github.com/JSL107/personal_agents/pull/679)에 기록된 2026년 9월 29일 실측에서 이 차이가 선명하게 드러나요.

| 집계 그룹 | 표본 수 | 미탐 재현율 |
| --- | ---: | ---: |
| 전체 | PR 설명에 별도 총수 미기재 | 31% |
| diff가 잘리지 않은 그룹 | 13건 | 59% |
| diff가 잘린 그룹 | 12건 | 0% |

같은 자료에는 `not-in-diff`로 해석된 미탐 8건이 모두 잘린 그룹에 속했고 전체 diff에서 50,000바이트 뒤에 있던 파일로 확인됐다고 적혀 있어요. 다만 이 8건이 표의 각 분모에 정확히 어떻게 들어갔는지는 제공된 내용만으로 재구성할 수 없어요.

전체 재현율 31%만 보면 모델이 결함의 약 3분의 1만 찾은 것처럼 보여요. 하지만 안 잘린 그룹의 59%와 잘린 그룹의 0%를 합친 결과라면 모델의 탐지 능력과 입력 가시성이 한 값에 섞여 있어요. 입력에 없던 줄을 찾지 못한 것까지 모델의 실패로만 계산하면 프롬프트 변경 효과가 실제보다 낮게 나타나요.

#679는 기존 전체 점수를 남겨 두고 각 라벨을 `diffTruncated` 여부에 따라 잘린 그룹과 안 잘린 그룹으로 나눠 집계했어요. 과거 보고서와 이어서 볼 전체 지표는 유지하면서 모델 성능을 판단할 때는 입력이 온전했던 그룹을 따로 볼 수 있게 한 거예요.

잘린 그룹은 모델 품질보다 입력 파이프라인의 한계를 보여 주는 운영 지표로 볼 수 있어요. 잘린 비율이 높다면 프롬프트를 더 다듬기 전에 파일별 분할, 관련 구간 선택, diff 예산 조정 같은 입력 전략을 검토해야 해요.

### 잘림 판정은 바이트인데 절단은 글자 수였다

그룹을 제대로 나누려면 `diffTruncated`부터 정확해야 해요. 당시 구현은 잘림 여부를 판단할 때와 실제로 자를 때 서로 다른 단위를 썼어요.

`getPullRequestDiff`와 `compareCommits`는 `Buffer.byteLength(diff) > maxBytes`로 한도 초과 여부를 판단하면서 실제 내용은 `diff.slice(0, maxBytes)`로 잘랐어요. 앞에서는 바이트 수를 재고 뒤에서는 JavaScript 문자열의 UTF-16 코드 단위 수로 자른 거예요. `maxBytes`라는 변수 하나에 서로 다른 기준을 적용한 셈이에요.

[PR #680](https://github.com/JSL107/personal_agents/pull/680)의 사례에서 대상 서비스의 한 PR diff는 56,814바이트, 49,462자였어요. 바이트 기준으로는 50,000바이트를 넘어 `truncated=true`였지만 글자 수를 기준으로 한 `slice(0, 50000)`에는 문자열 전체가 들어갔어요. 보고서는 “잘렸다”고 표시했는데 모델은 전문을 받은 거예요.

반대 상황도 생길 수 있어요. PR 설명에서는 한글 한 글자를 3바이트로 계산하면 5만 글자가 최대 약 150KB에 이를 수 있다고 지적해요. 글자 수를 기준으로 5만 개를 자르면 `50,000 bytes`라는 설정 이름과 달리 실제 모델 입력이 바이트 한도를 크게 넘을 수 있어요.

#680은 잘림 판정과 실제 절단에 모두 UTF-8 바이트 기준을 적용했어요. `/review-pr` 프롬프트에 표시하는 전달량도 문자열 길이 대신 바이트 단위로 맞췄어요. 보고서의 `truncated` 판정, 모델이 실제로 받은 입력, 사용자에게 안내하는 숫자가 모두 같은 단위를 가리키게 한 거예요.

### 기준선 비교도 안 잘린 미탐끼리 해야 했다

분리 집계를 보고서에 추가한 뒤에도 기준선 판정은 한동안 전체 미탐 재현율을 사용했어요. `compareWithBaseline`이 `trials.missed`를 비교했기 때문이에요. 잘린 그룹의 0%가 섞이면 안 잘린 그룹에서 나타난 모델 성능 변화가 전체 평균에 묻혀요.

[PR #681](https://github.com/JSL107/personal_agents/pull/681)은 미탐 기준선의 비교 대상을 `trials.byDiffTruncation.missed.intact`로 바꿨어요. 현재 보고서와 기준선에서 diff가 안 잘린 미탐 그룹끼리 비교해요. 기준선이 분리 집계 이전 형식이면 전체 값을 대신 가져오지 않고 판단 불가로 처리해요.

이 선택으로 이전 보고서와의 호환성은 일부 포기해요. 구형 기준선의 전체 재현율을 가져오면 숫자는 계속 출력할 수 있지만 서로 다른 모집단을 비교하게 되니까요. 새로운 분리 기준선을 한 번 만든 뒤부터 같은 조건으로 비교해야 해요.

범위를 벗어났을 때 어느 방향으로 변했는지도 표시했어요. 지표마다 좋아지는 방향이 다르기 때문이에요.

| 라벨 | 측정 의미 | 좋은 방향 |
| --- | --- | --- |
| `REJECTED` | 과거 오탐이 다시 발생하는 비율 | 낮을수록 좋음 |
| `FIXED` | 과거 정탐을 다시 발견하는 비율 | 높을수록 좋음 |
| `MISSED` | 과거 미탐을 새로 발견하는 비율 | 높을수록 좋음 |

기존 출력은 결과가 기준선의 변동 범위를 벗어났다는 사실만 알려 줬어요. 사용자는 `REJECTED`와 `FIXED`의 방향을 매번 반대로 해석해야 해서 개선과 악화를 뒤집어 읽을 수 있었어요. #681 이후에는 범위를 벗어난 결과가 좋은 쪽인지 나쁜 쪽인지까지 표시하고 콘솔에서 다음 규칙을 확인할 수 있어요.

- 나쁜 방향으로 범위를 벗어나면 변경을 반려해요.
- 좋은 방향으로 벗어나면 한 번 더 실행해 확인해요.
- 변동 범위 안이면 효과 없음 또는 측정 불가로 해석해요.
- 비교할 수 있는 분리 기준선이 없으면 판단 불가로 남겨요.

좋은 방향으로 변했더라도 바로 승인하지 않는 이유는 출력이 확률적으로 달라지기 때문이에요. 첫 번째 이탈은 개선 후보를 발견한 것이고 추가 재실행은 그 값이 우연한 회차 변동인지 확인하는 절차예요. 제공된 근거에는 이 변경 이후 프롬프트의 최종 성능 향상 수치가 없어요.

### 아직 끝나지 않은 검증

평가 구조는 나아졌지만 재현 가능성 검증은 아직 끝나지 않았어요. PR 20건 규모의 검증, 이슈 #52의 체크리스트 승인, #153의 정합성 재현, #1149의 검증 기록이 남아 있어요. 워커가 연속 실패했다는 기록도 있지만 실패 원인과 재시도 결과는 제공된 자료에 없어요.

중복 입력을 어떻게 처리하는지, 실행 중 실패했을 때 부분 결과를 보존하는지, 재시작할 때 완료된 회차를 건너뛰는지도 확인할 수 없었어요. 반복 측정 도구를 운영 수준에서 신뢰하려면 다음 조건을 따로 검증해야 해요.

- 동일한 미탐이 목록에 중복됐을 때 분모를 어떻게 계산하는가
- N회 실행 도중 일부 회차가 실패해도 보고서를 생성하는가
- 재시작할 때 처음부터 호출하는가, 완료한 회차를 재사용하는가
- 기준선과 현재 보고서의 표본 구성이 다르면 비교를 거부하는가
- UTF-8 다중 바이트 문자 경계에서 절단한 diff가 유효한 문자열로 남는가
- `headSha`가 없거나 과거 커밋을 가져오지 못하면 어떤 상태로 기록하는가

이 목록은 현재 구현에 결함이 있다고 단정하는 내용이 아니에요. 남은 재현·기록 작업과 함께 다음 평가에서 확인할 조건이에요.
